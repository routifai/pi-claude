Omnigent Memory Architecture

How Omnigent handles memory when a session runs across more than one harness — Claude, Pi, or any other agent it wraps. Covers short-term (conversational) memory, long-term (cross-session) memory via Hindsight, and what changes if Mem0 is used instead.

Two kinds of memory

The word "memory" covers two different problems. Omnigent solves them differently.

ScopeOne conversation / one sessionAcross sessions, indefinitely

Short-term memory: one session, shared across harnesses

Every harness keeps its own native conversation log, independently of Omnigent. Omnigent keeps a second, separate record in parallel — and that second record is what actually gets shared when a harness switch happens.

Each harness already has its own log

Both are real, both are JSONL, and both use different internal schemas. Neither format is something the other harness — or anything outside that harness — reads directly.

In parallel, Omnigent keeps its own copy

Regardless of which harness is running, every turn is also translated into a single common shape and written into the session record Omnigent owns:

The common message is what gets stored in the session's persistence layer (Postgres or SQLite). That store is the actual shared memory — not either harness's own log.

What happens when the harness switches

Switching harness mid-session means the session's existing memory has to become visible to a harness that has never seen it before.

  1. A switch request is issued for the active session, naming the target harness (for example, Pi → Claude).
  2. Omnigent looks up the session's stored history — the common-format record accumulated so far, independent of which harness produced it.
  3. A new executor is started for the target harness.
  4. Omnigent reconstructs that history inside the target harness's own native session format — not as extra prompt text, but written into its own log, so the harness's normal context-loading behaves as if it had been running the whole conversation itself.
  5. The session record is updated with a marker confirming history was carried across.
  6. The new harness responds with full awareness of everything said so far, including turns produced by the previous harness.
The unit of memory is the session, not the harness. A harness never owns the conversation — it's handed a reconstruction of it on demand. That's what makes "one memory across multiple harnesses" possible without either harness needing to know about the other.
Known limitation. Step 4 depends on the new executor being able to read the source harness's environment. In sandboxed or isolated-compute setups, a fork that provisions a brand-new sandbox may not have access to the original session's native log, and the reconstruction can silently fail — the new harness then starts with no carried history. Worth testing explicitly under whatever sandboxing model is chosen for a production deployment.

Long-term memory: Hindsight is the only native integration

As of now, Hindsight is the only long-term memory provider with first-party support in Omnigent. No other memory provider ships as a built-in.

It's added as three built-in tools, configured per agent:

These tools are intercepted and executed by the Omnigent runner directly — before the call ever reaches the harness. That's what makes it work with any harness Omnigent wraps, including ones with no memory feature of their own: the harness only needs to see three ordinary tools in its tool list, decide when to call them, and read the result back.

Sharing works the same way as the short-term case, but at a different layer: point every agent's bank_id at the same value, and every harness reads and writes the same long-term bank. Unlike the session record, this memory survives after the session ends and is retrievable from an entirely separate, future session.

If Mem0 is considered instead

Mem0 has no equivalent native integration with Omnigent today.

Mem0 ships as an MCP server. Omnigent supports declaring MCP servers per agent, so Mem0 can be added the same way any external tool is added — but that's a materially different arrangement from Hindsight's runner-level interception:

  • No automatic interception. The harness itself must support and choose to call the MCP tool — Omnigent doesn't execute it on the harness's behalf.
  • Cross-harness sharing isn't structural. It depends on every agent's MCP config pointing at the same Mem0 user/namespace, set up manually — nothing enforces this the way bank_id does for Hindsight.
  • No storage lock-in. Mem0 lets you bring your own vector database; Hindsight is Postgres-only.
  • Larger ecosystem, more retrieval maturity outside of Omnigent specifically — relevant if Mem0 is already used elsewhere in the stack.

In short: Hindsight is the lower-effort path specifically because Omnigent already wired it in. Mem0 is viable but means building and maintaining the cross-harness sharing behavior that Hindsight gets by default.
