Registering Tools and Overriding Behavior Per Harness

Two extension points in Omnigent: giving a specific harness custom tools, and giving a specific harness behavior it doesn't have natively — using Pi's missing "plan mode" as the worked example. Covers the documented path, where it stops, and what has to be wired manually when driving executors directly instead of through Omnigent's full server/session runtime.

Background/ Custom tools/ Skills/ Behavior overrides/ Summary/ Recommendation

Background: Omnigent's real extension points

Two documented mechanisms are relevant here, both designed for Omnigent's full server/session runtime.

  • Custom Agents — attach Python-function-backed tools to an agent via YAML.
  • Contextual Policies — Python functions that intercept every tool call, LLM request, or file operation and decide ALLOW / ASK / DENY, in real time, across any harness.
The gap this document covers: when driving a harness executor directly (ClaudeSDKExecutor, PiExecutor, etc.) rather than through the full runtime, the YAML resolves correctly, but the automatic wiring these features rely on has to be reproduced by hand.

One contract difference between harnesses

Pi's tool-executor callback accepts either a synchronous or an async function. Claude's requires async — a synchronous dispatcher fails with "object dict can't be used in 'await' expression". Use an async def dispatcher(...) for anything that needs to work across both.

Confirmed working for Claude too, but through a different mechanism: Claude surfaces custom tools as MCP-style tools, discovered dynamically via its own tool-search call (mcp__omnigent__<tool_name>), rather than a direct tool list the way Pi receives them. Same YAML input, same dispatcher pattern, different internal transport.

Registering skills per harness

Skills (self-contained directories with a SKILL.md file) load through a separate, undocumented-at-the-executor-level path: the bundle_dir constructor parameter.

Internally, the resolver walks <bundle_dir>/skills/ and appends a --skill <path> flag for every subdirectory containing a SKILL.md. skills_filter="all" (the default) adds every bundled skill explicitly and leaves the harness's own auto-discovery running.

Do not trust the harness's own self-report. Asking it directly ("what skills do you have?") can return "none" even when skills are correctly loaded and actively shaping the response. Confirm by inspecting the executor's actually-resolved CLI arguments directly, or by giving it a task that should invoke the skill's real content and checking whether the response reflects that content.

Overriding behavior per harness: the plan-mode case

Claude has a native switch

Confirmed to genuinely change behavior: under permission_mode="plan", the executor attempts an ExitPlanMode tool call and writes a plan document instead of performing the requested edit directly.

Pi has no equivalent

No permission_mode parameter, no reference to plan/permission modes anywhere in Pi's executor source — confirmed by inspection, not just absence of documentation. Asking the harness directly reports zero modes available, consistent with the source. A genuinely missing capability, not an undiscovered wiring path.

The real extension point: Contextual Policies

Omnigent's documented Policy system is the right shape for this, and it's harness-agnostic by design:

The pattern repeats across every capability tested: the underlying capability generally exists, but driving an executor directly instead of through Omnigent's full session runtime means whatever that runtime normally wires automatically has to be built by hand, at the same interception points the runtime itself would use.

Recommended pattern going forward

Rather than wiring _tool_executor ad hoc per agent, a small shared helper is worth building once.

This keeps tool registration and behavior overrides in one reusable place, keyed by harness, matching the shape of Omnigent's own documented Policy system closely enough that migrating to the full server runtime later — if that becomes the right call — is a drop-in change rather than a rewrite.
